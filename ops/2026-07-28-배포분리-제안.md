# 배포 분리 제안 — 개발 트리와 라이브 트리를 나눈다 (2026-07-28, 도진-인프라)

> **상태: 제안. 적용 전 사용자 승인 필요** (systemd·라이브 구동 경로 변경).

## 문제

`/root/murmur-stack → /root/ClaudeCompany` 심링크라서 라이브 서비스(murmur-web :8000,
organt-runner)가 **세션들이 편집하는 바로 그 트리**를 import한다. murmur-dev는 심링크 없이
`/root/ClaudeCompany` 하드코딩. 그 결과:

- 파일을 저장하는 순간 이미 라이브다. 커밋·검증·승인 전인데도.
- 아무 세션이나 러너를 재시작하면 그 시점 디스크의 반쯤 고친 코드가 부팅된다(07-28 실제 위험 노출).
- pre-commit 훅은 **커밋**을 막을 뿐, 디스크 편집이 라이브에 닿는 것은 못 막는다.
  세션 격리(worktree)로 정본 편집 자체가 줄지만, 병합 직후 코드가 곧장 라이브가 되는 구조는 남는다.

## 제안

```
/root/ClaudeCompany   ← 정본(병합 대상). 세션은 /root/wt/<세션>에서 작업.
/root/live            ← 라이브 전용 체크아웃(신규 clone). 서비스는 여기서만 구동.
/root/murmur-stack    ← 심링크를 /root/live 로 전환.
```

- `ops/deploy.sh <commit-ish>`: 정본에서 검증(verify.sh) 통과한 커밋만 `/root/live`로
  fetch+checkout → 프론트 빌드 → (플래그 시) 서비스 재시작. 명시적 실행 없이는 라이브 불변.
- murmur-dev(개발 서버 :8001)는 지금처럼 정본/worktree를 봐도 된다 — 그게 용도다.
- `.venv`: 초기엔 정본 venv 심링크로 시작(디스크 절약), 의존성 변경이 잦아지면 live 전용 venv 분리.

## 적용 절차(승인 후)

1. `git clone /root/ClaudeCompany /root/live && git -C /root/live remote set-url origin /root/ClaudeCompany`
   (murmur 서브레포 동일) + venv 심링크 + 프론트 빌드
2. 다른 세션 작업 중 아닌 시점에: `ln -sfn /root/live /root/murmur-stack` → `systemctl daemon-reload`
   → murmur-web·organt-runner 재시작
3. murmur-dev.service의 WorkingDirectory는 정본 유지(개발 서버) — 변경 불필요
4. 롤백: 심링크를 `/root/ClaudeCompany`로 되돌리고 재시작 (1줄)

## 비용/리스크

- 디스크: 트리 1벌 추가(node_modules·venv 제외 시 수백 MB 수준).
- git-backup.service는 정본만 push — 영향 없음.
- 라이브 반영이 한 단계 늘어난다(deploy.sh 실행) — 이것이 목적이다.

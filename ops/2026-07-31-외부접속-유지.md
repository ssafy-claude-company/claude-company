# 외부 접속이 스스로 살아나게 (2026-07-31, 현준-4)

## 무엇이 문제였나

공유기가 재시작하면 UPnP 포트 매핑이 통째로 사라진다. 실측으로 07-30 22:53 WAN 재시작 때
그렇게 murmur가 밖에서 끊겼다. 서버는 멀쩡했다 — LAN 주소로는 80·443 모두 정상 응답했고,
인증서도 유효했고, DNS도 공인 IP와 일치했다. 끊긴 곳은 공유기 바깥이었다.

사람이 알아채기까지 한 시간 넘게 걸렸다. 첫 화면이 아니라 접속 자체가 안 되는 종류라
내부 감시로는 안 잡힌다.

## 근본 해결과 그때까지의 방편

근본은 공유기 관리 화면의 **정적 포트포워딩**이다(443·80 → 이 서버, DHCP 고정 할당 함께).
그건 사람 손이 필요하다. 그때까지 스스로 되살아나게 한다.

## 어떻게

`upnp-ensure`가 매핑을 확인하고 없으면 다시 건다. 지키는 것:

- **주기로 확인한다.** 끊긴 사례가 '공유기 재시작'이지 '이 서버 재부팅'이 아니었다 —
  부팅 때만 걸면 그 사고를 못 막는다. 5분마다 돈다.
- **랜 주소를 박지 않는다.** DHCP로 바뀌면 엉뚱한 곳에 매핑이 걸린다. 실제 경로에서 뽑는다.
- **멱등하다.** 이미 걸려 있으면 건드리지 않는다.
- **조용한 성공은 안 적는다.** 5분마다 도는 것이라 로그가 사실을 덮는다. 재등록과 실패만 남긴다.

## 실측

일부러 443 매핑을 지우고(공유기 재시작 재현) 스크립트를 돌렸다.

```
443 매핑 삭제됨 → 남은 443 매핑: 0
upnp-ensure 실행
  0 TCP    80->192.168.0.5:80
  3 TCP   443->192.168.0.5:443
로그: 매핑 재등록 443 -> 192.168.0.5:443
```

## 설치

```
sudo install -m 0755 ops/sandbox/host/upnp-ensure /usr/local/sbin/upnp-ensure
sudo install -m 0644 ops/sandbox/host/upnp-ensure.service /etc/systemd/system/
sudo install -m 0644 ops/sandbox/host/upnp-ensure.timer /etc/systemd/system/
sudo install -m 0644 ops/sandbox/host/logrotate-upnp-ensure.conf /etc/logrotate.d/upnp-ensure
sudo systemctl daemon-reload && sudo systemctl enable --now upnp-ensure.timer
```

되돌리기: `systemctl disable --now upnp-ensure.timer`

## 실제로 밖에서 열리는지 확인한다

매핑이 있다고 밖에서 열리는 것은 아니다. 07-30 사고의 진짜 문제는 '끊긴 것'이 아니라
**한 시간 넘게 아무도 몰랐던 것**이었다 — 서버 안에서 보면 다 정상이라 내부 감시로는
안 잡힌다. 공인 주소로 실제로 두드려 보고, 안 열리면 systemd 실패로 남긴다(로그 파일만
쓰면 아무도 안 본다).

자가 복구가 먼저 걸리므로 경보는 **고칠 수 없는 상태**에서만 울린다. 매핑이 사라진
정도는 조용히 되살리고, 되살려도 안 열리면 그때 운영자를 부른다.

경보 경로는 `UPNP_PROBE_HOST`로 시험할 수 있다 — 시험할 수 없는 경보는 켜져 있다고
믿을 뿐 지켜 주지 않는다. 실측:

```
UPNP_PROBE_HOST=192.0.2.1 upnp-ensure
  → 외부 도달 실패: https://192.0.2.1/ 응답 000   (exit 1)
정상 대상 → exit 0, 조용함
```

## 남는 것

이것은 방편이다. UPnP를 쓴다는 것은 공유기가 그 요청을 계속 받아 준다는 전제 위에 있다.
정적 포워딩이 걸리면 이 타이머는 하는 일이 없어지고(멱등), 그때 꺼도 된다.

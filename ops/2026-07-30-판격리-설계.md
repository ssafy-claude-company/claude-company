# 판 격리 설계 — 작품 단위 커널 경계와 egress 통제

작성 2026-07-30, 현준-4. 근거는 라이브 감사 로그 실측(run 11,327건)과 호스트 점검이다.
이 문서는 제안이다. 구현 전 승인이 필요하다.

---

## 1. 왜 지금인가

봇 실행 계정을 root에서 `organt`로 내렸고(2026-07-30 착지), 봇 셸은 bwrap으로 그 판의
작업공간만 본다. 남은 구멍은 두 개이고, 둘 다 **판(작품) 사이의 경계**에 관한 것이다.

격리 단위가 봇이 아니라 판이라는 것은 실측으로 확인했다. 작업공간 90개가 `p-0XX-슬러그`
(69개)와 신규 판(20개)으로 나뉘어 있고 봇 이름 폴더는 없다. 봇은 여러 판을 돌아다니고,
지켜야 할 것은 판에 든 작품이다.

이 경계는 봇 대여·작품 판매로 확장할 때 신뢰의 근본이 된다. 남의 봇을 들이는 순간
"그 봇이 내 작품에 닿는가"가 곧 플랫폼의 약속이다. 기능보다 먼저다.

---

## 2. 지금 무엇이 비어 있나 (실측)

### 2.1 판끼리 커널 경계가 없다

작업공간 90개가 한 디렉터리 아래 평평하게 있고 소유자가 섞여 있다.

    nobody  50개
    root    40개

`nobody` 50개는 root 시절 `_chown_tree`가 샌드박스 강등용으로 넘긴 결과다. 즉 모든 판이
같은 신분을 공유한다. 지금 판 사이를 막는 것은 두 겹이다.

  - PreToolUse 훅: 네이티브 파일 도구(Read/Write/Edit/Glob/Grep)를 그 판의 cwd 안으로 제한
  - bwrap `--bind`: run 셸에는 그 판의 작업공간만 `/tmp/workspace`로 노출

둘 다 정책이다. 커널은 이 경계를 모른다. 훅이 새거나 바인드가 잘못되면 90개가 한꺼번에
노출된다.

### 2.2 egress가 열려 있다

샌드박스에 `--unshare-net`이 없어 호스트 네트워크를 그대로 쓴다. 실측:

    외부 IP 직결(https://1.1.1.1)        → 301  (통함)
    데이터 POST 유출 흉내                → 301  (통함)
    localhost murmur-web(:8000)          → 200  (통함)
    도메인 조회(getent)                  → 실패 (DNS만 안 됨)
    봇 제어 경로(/api/guide/, :8000 직결) → 403  (Django가 막음)

즉 봇은 작품 파일을 임의 IP로 내보낼 수 있다. 도메인은 안 되지만 IP를 알면 된다.
감사 로그에 run 명령 전문이 남아 사후 추적은 되지만, 막지는 못한다.

## 3. 실사용은 무엇을 요구하는가 (설계의 근거)

단순히 네트워크를 끊으면 봇의 주 작업이 죽는다. run 11,327건을 분류했다.

    네트워크가 필요한 run        3,250건 (28%)
      패키지·git 계열            1,818건
    URL 목적지 분포
      localhost                  1,567건
      자기 도메인(murmur·render)  2,116건
      그 외 외부                     53건

외부 임의 호스트는 **53건뿐**이고 그 전부가 아래다.

    16  www.notion.so          8  cdn.jsdelivr.net       4  example.com
     3  pypi.org               3  www.google.com         2  registry.npmjs.org
     2  fonts.googleapis.com   2  kenney.nl              2  cdnjs.cloudflare.com
     1  api.ipify.org          1  1.1.1.1               (나머지는 정규식·템플릿 오검출)

두 가지가 결정적이다.

**첫째, localhost가 주 검증 경로다.** 봇은 한 run에서 서버를 띄우고 다른 run에서 curl로
확인한다(127.0.0.1:4100 426건, localhost:3000 313건 등, 고유 호스트 111개). 그래서
`--unshare-net`을 그냥 넣으면 샌드박스마다 별개 netns를 받아 서로를 못 보고, 검증이 통째로
깨진다. 실패는 조용하다 — 봇은 원인을 모르고 약한 명령으로 우회한다(U-063 선례).

**둘째, 허용 목록이 현실적으로 짧다.** localhost + 자기 도메인 + 패키지 레지스트리 +
위 열 개 내외면 98%가 덮인다.

## 4. 제안

### 4.1 판별 netns (작품 경계를 커널에 세운다)

판마다 지속 네트워크 이름공간을 하나 둔다. 그 판의 봇 run은 모두 그 netns에서 돈다.

  - 같은 판의 봇은 서로의 localhost 서버를 본다 → 주 검증 흐름이 살아난다
  - 다른 판의 서버는 보이지 않는다 → 지금 없는 경계가 생긴다
  - 호스트 서비스(murmur-web·postgres)도 기본적으로 보이지 않는다
  - 외부는 뒤의 관문을 통해서만 나간다

지금은 모든 판이 호스트 netns를 공유하므로, 판 A의 봇이 판 B가 띄운 개발 서버에 접속할 수
있다(포트만 알면 된다). 실측 고유 포트가 111개라 우연한 충돌·간섭도 이미 가능한 상태다.

### 4.2 목적지 관문 (egress allowlist)

netns 밖으로 나가는 길은 하나로 모으고 목적지를 허용 목록으로 제한한다. 프록시 방식이
현실적이다 — npm·pip·git·curl이 모두 `HTTP_PROXY`를 따르고, 따르지 않는 도구는 그대로
막히는 것이 기본 거부와 맞다.

초기 허용 목록(위 실측에서 도출):

    자기 것        murmur.dojin-mini.shop · atelier.dojin-mini.shop · murmur-ai.duckdns.org
                   *.onrender.com
    패키지         registry.npmjs.org · pypi.org · files.pythonhosted.org
                   github.com · codeload.github.com · objects.githubusercontent.com
                   playwright 다운로드 호스트 · deb 미러
    정적 자산      cdn.jsdelivr.net · cdnjs.cloudflare.com · fonts.googleapis.com
                   fonts.gstatic.com
    조사           www.notion.so · www.google.com

허용 목록은 설정으로 두고 판별로 좁힐 수 있게 한다(대여한 봇이 도는 판은 더 좁게).

### 4.3 판별 UID (파일 경계를 커널에 세운다)

작업공간 소유자를 판별 uid로 바꾼다. `_chown_tree`가 지금은 단일 강등 계정으로 넘기는데,
판 id에서 uid를 결정하도록 바꾼다. 그러면 훅이 새더라도 판 A의 프로세스가 판 B의 파일을
열 수 없다.

방식은 두 가지다. 판별 고정 uid를 미리 할당하는 쪽이 디버깅이 쉽고, systemd `DynamicUser`
계열은 관리가 편하지만 영속 소유권과 맞추기가 번거롭다. 판 수가 늘어나는 서비스라 전자를
권한다.

## 5. 위험과 순서

가장 큰 위험은 **조용한 실패**다. 네트워크나 권한이 막히면 봇은 오류를 사람에게 알리지 않고
검증을 포기하거나 약한 명령으로 우회한다. tmpfs 권한 하나로 봇이 검증을 통째로 포기했던
선례가 있다(U-063).

그래서 순서를 이렇게 둔다.

    1) 판별 netns + 관문을 만들되 **기본 off**(env 플래그). 켠 판만 적용한다.
    2) 판 하나에서 실사용 흐름을 통과시킨다 — 서버 띄우기·localhost curl·npm install·git·
       playwright. 실패하면 허용 목록을 넓힌다.
    3) 관문이 막은 요청을 감사에 남긴다. 무엇이 부족한지 로그로 보인다.
    4) 전체 판으로 켠다.
    5) 그다음 판별 UID로 파일 경계를 세운다(netns가 안정된 뒤).

각 단계는 플래그로 되돌린다. 오늘 게이트 두 개를 백필 후 켜서 동작 변화 0으로 전환한 방식과
같다.

## 6. 승인이 필요한 결정

  - 판별 netns를 도입할지(대안: 호스트 netns 유지 + uid 기준 방화벽 — 판끼리는 여전히 무경계)
  - 허용 목록의 초기 범위(위 목록에서 빼거나 더할 것)
  - 판별 UID 방식(고정 할당 vs DynamicUser)
  - 적용 시점 — 봇이 도는 중에는 판별 netns 전환이 그 판의 작업을 끊는다

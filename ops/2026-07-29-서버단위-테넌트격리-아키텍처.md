# murmur 서버(Project) 단위 테넌트 격리 아키텍처 — 제안

작성 2026-07-29. 대상: dojin-mini(4코어/14GB) 단일 호스트.
현황 규모: 서버(Project) 12개(공개 6/비공개 6), 사람 472명, 봇(Agent) 32기.

이 문서는 제안이다. 확정 설계가 아니며 채택 여부는 사용자가 정한다.
사용자가 정한 격리 단위는 **서버 = murmur의 Project(P-번호)** 다.

## 적용 현황 (2026-07-29)

| 단계 | 상태 | 반영 시점 |
|---|---|---|
| 1. 자원 구획(cgroup) | 적용 완료 | 즉시 (커널 반영 확인) |
| 2. 서버 단위 원장 | 코드·마이그레이션 완료, 테이블 생성됨 | murmur-web 재시작 후 적립 시작 |
| 4. 봇풀 테넌트 상한 | 코드 완료, 기본 비활성(env 0) | organt-runner 재시작 + env 설정 후 |
| 잔여 표면 봉합 | 코드 완료 (PreToolUse 인자 기반 경계) | organt-runner 재시작 후 |
| 3. 서버별 쿼터 강제 | 미착수 | 원장 데이터가 쌓인 뒤 한도값 실측으로 결정 |
| 5. 컨트롤/워커 분리 | 미착수 | 워크스페이스 이전 타이밍 결정 필요 |
| 6. 금고 키 범위·egress | 미착수 | |

**1단계 적용값**: murmur-web·murmur-sse·postgresql@18-main `MemoryMin=512M`,
nginx `MemoryMin=256M`, 넷 다 `CPUWeight=1000`. organt-runner `MemoryHigh=4G`,
`MemoryMax=5G`, `CPUWeight=100`, `TasksMax=256`. 프로덕션 몫을 커널이 보장하므로 봇 폭주 시
OOM은 봇 구획 안에서만 난다.

**2단계 결과**: `ProjectUsageLedger(project, period)` 신설. 같은 report_usage 증분을 사람
축(청구, 종전)과 채널 축(관측, 신규)에 나눠 적는다. 채널 축은 owner 유무와 무관하게 적립해
주인 없는 시스템 판의 비용이 더 이상 원장에서 사라지지 않는다. 관측 적립은 savepoint 안에서
DB 오류를 삼켜, 배포와 migrate 시점이 어긋나도 과금 적립을 끊지 않는다.

**4단계 결과**: `ORGANT_MAX_SUBPROCS_PER_TENANT`(기본 0=비활성). 켜면 채널 하나가 쓸 수 있는
동시 슬롯이 제한된다. 획득 순서는 테넌트 → 전역 고정(반대면 전역 슬롯을 쥔 채 대기해 남의
채널까지 굶는다). 테넌트를 모르는 턴은 전역 상한만 받는다.

**잔여 표면 봉합**: 작업공간 경계 검사가 도구 이름(Read/Glob/Grep/Write/Edit)에 걸려 있어,
허용 목록에 새 네이티브 파일 도구가 추가되면 검사가 비껴갔다. 이름 대신 '경로 인자를 들고
왔는가'로 한 겹 더 막아 새 도구에 기본 차단이 걸리게 했다. MCP 흐름 도구는 제외해 기존 동작
불변.

**검증**: 브레인 pytest 968, system unittest 87, murmur sns 676 전부 통과.

**재시작 유의**: 2·4·봉합은 프로세스 재시작 후에 효력이 생긴다. 재시작 시점에 murmur 레포
작업 트리에 다른 세션의 미완 변경이 함께 올라가므로, 그 세션 작업이 정리된 뒤에 재시작한다.

## 0. 먼저: 이미 잘 돼 있는 것 (정정)

설계에 앞서 현재 방어선을 정확히 기록한다. 앞선 세션에서 "봇이 root라 위험"이라고 요약했으나
실제 코드를 읽으니 **애플리케이션 레벨 격리는 이미 상당히 촘촘하다.** 이 사실이 아래 설계의
출발점을 바꾼다 — 새로 만드는 게 아니라 *커널 백스톱을 덧대는* 일이다.

| 방어 | 구현 | 위치 |
|---|---|---|
| 봇에게 셸(`Bash`) 미허용 | `WORKER_BASE_TOOLS`에 Bash 없음(Read/Write/Edit/Glob/Grep/ToolSearch/Web*) | `organt/builder.py:23` |
| 셸은 샌드박스 경유만 | `mcp__guide__run` → bwrap(`--ro-bind / /`, `/root`를 tmpfs로 가림, 워크스페이스만 `--bind`) + setpriv로 nobody·capability 0 | `system/guide_tools.py:153-232` |
| 네이티브 읽기/탐색도 작업공간 경계 | PreToolUse 훅이 Read/Glob/Grep을 `_within(cwd, target)`로 차단. realpath 기반이라 심링크 우회 불가. Glob 패턴 접두까지 검사 | `system/permissions.py:158-177` |
| 쓰기도 같은 경계 | Write/Edit 동일 게이트 | `system/permissions.py:180-` |
| run 셸 env에서 비밀 제거 | `_scrubbed_run_env()` — `*KEY`·`*TOKEN`·`GH_PAT` 등 제거 | `guide_tools.py:81-88` |
| 봇 기억의 흐름 격리 | 세션을 `session_scope`별로 분리 — 같은 봇이 두 프로젝트에서 동시에 일해도 기억이 안 섞임 | `builder.py:65-69` |
| 스폰 바운딩 | 전역 세마포어 8 + MemAvailable floor | `organt/botpool.py` |
| 비용 봉투 | `max_turns` 300/500, `ORGANT_TURN_BUDGET_USD=1.0` | `builder.py:50-64` |

특히 `permissions.py:152-157` 주석은 이미 정확히 이 위협을 적어뒀다 — "봇이 `Read
/etc/murmur-web.env`로 러너 비밀을 통째로 탈취 가능(파일 도구는 러너 인프로세스 root라 run
셸의 강등 방어와 무관)". 2026-07-18 감사에서 잡혔고 막혀 있다.

**따라서 남은 문제는 "격리가 없다"가 아니라 "격리가 전부 한 겹, 그것도 in-process 훅에
걸려 있다"이다.**

## 1. 남은 격차 (서버 단위 관점)

### G1. 커널 백스톱 부재 — 훅이 뚫리면 전부 뚫린다
파일 도구 경계는 `permissions.py`의 PreToolUse 훅 **하나**가 전부다. 이 훅은 러너 프로세스
안에서 root 권한으로 돈다. 다음 중 하나만 성립하면 전 테넌트가 동시에 노출된다:
- `WORKER_BASE_TOOLS`에 새 도구를 추가하면서 훅의 검사 목록(`Read/Glob/Grep/Write/Edit`)에
  안 넣는 경우 — 목록이 **화이트리스트가 아니라 이름 하드코딩**이라 조용히 새는 구조다.
- 훅 예외가 삼켜지는 경로.
- SDK가 새 파일 접근 도구를 기본 활성화하는 경우.

커널은 이 경계를 전혀 모른다. 봇 프로세스는 uid 0이고 `/etc/murmur-web.env`를 실제로 읽을
수 있다 — 다만 훅이 요청을 거부할 뿐이다. 방어가 "정책"이지 "능력 제거"가 아니다.

### G2. 전 테넌트가 UID 하나(root)를 공유
워크스페이스는 프로젝트별 디렉터리로 나뉘어 있지만 소유자가 전부 root다. 훅을 우회한 실행
경로가 하나라도 생기면 **12개 서버 전부의 산출물·문서에 즉시 접근**된다. 테넌트 간 파일
경계를 커널이 강제하지 않는다.

### G3. 사용량이 서버 단위로 안 잡힌다 (사용자가 지목한 문제)
`UsageLedger`의 키는 `(person, period)`다. 봇 턴 비용은 `Project.owner`에게 귀속되므로
**사람은 막을 수 있어도 서버는 못 막는다.** 한 서버가 폭주해도 그 서버만 정지시킬 수단이
없고, 소유자가 여러 서버를 가지면 어느 서버가 태웠는지 원장으로 분리되지 않는다. 사용자가
말한 "서버 단위 사용량 폭 제한"은 현재 스키마로 구현 불가다. **이게 이번 요구의 핵심 격차다.**

### G4. 시끄러운 이웃 — botpool 세마포어가 전역
동시 서브프로세스 상한 8이 전 서버 공통이다. 서버 A가 8슬롯을 다 쓰면 서버 B~L은 대기한다.
서버별 동시성 보장(reservation)도, 상한(cap)도 없다.

### G5. 러너 하나가 모든 테넌트의 금고 키를 쥔다
`organt-runner` 프로세스 env에 `ORGANT_VAULT_KEY`가 있고, 이 키로 모든 프로젝트·사람의
시크릿을 복호한다. 프로세스 하나가 전 테넌트 비밀의 단일 실패점이다. `ProjectEnv`로 범위
분리는 돼 있으나 복호 능력은 분리돼 있지 않다.

### G6. 유출 경로가 열려 있다 (egress)
`WORKER_BASE_TOOLS`에 `WebFetch`/`WebSearch`가 있다. 워크스페이스 안의 내용을 읽어 외부
URL로 보내는 것은 훅이 막지 않는다(읽기 경계는 워크스페이스 안이므로 정당한 접근으로 보인다).
서버 A의 산출물이 외부로 나가는 경로가 정책상 비어 있다.

## 2. 목표

사용자가 말한 네 가지를 설계 목표로 옮기면:

1. **배포·봇이 서버 단위로 관리** → 실행 주체(UID)·자원 구획(cgroup)·수명이 서버마다 분리
2. **사용량 폭 제한** → 원장에 서버 차원 추가 + 서버별 쿼터 강제
3. **타 서버 정보 탈취 차단** → 커널 레벨 FS 경계(훅과 독립적인 2차 방어)
4. **원 서버(호스트) 공격 차단** → 테넌트 워크로드가 root를 못 얻고, 호스트 자원을 못 고갈

## 3. 제안 아키텍처: 컨트롤 플레인 / 테넌트 워커 분리

### 3.1 구조

현재는 러너 **한 프로세스**가 12개 서버의 모든 봇을 root로 돌린다. 이걸 두 층으로 쪼갠다.

```
[컨트롤 플레인]  organt-control.service   (비특권 유저 `organt`)
   역할: 채널 폴링, 위임 판단, 어느 테넌트를 깨울지 결정, 사용량 집계
   가지지 않는 것: 테넌트 금고 키, 테넌트 워크스페이스 쓰기 권한
        │
        │ systemd-run --unit=organt-tenant@P-032 (transient, on-demand)
        ▼
[테넌트 워커]   organt-tenant@P-032.service   (UID: organt-p032, 전용)
   역할: 그 서버의 봇 턴만 실행
   범위: /var/lib/organt/tenants/P-032 만 접근 가능
   자원: tenant-P-032.slice (MemoryMax/CPUQuota/TasksMax)
   수명: 일이 있을 때 기동 → 유휴 N분 후 종료 (콜드)
```

핵심은 **테넌트 워커가 서버마다 별개 UID·별개 cgroup·별개 수명**을 갖는 것이다. 이러면
사용자가 말한 네 목표가 전부 커널 레벨에서 성립한다.

### 3.2 각 격차에 대한 대응

**G1·G2 (커널 백스톱 / UID 공유)**
테넌트 워커를 프로젝트별 전용 UID로 실행한다. systemd 템플릿 유닛 `organt-tenant@.service`에:
```
User=organt-p%i                    (또는 DynamicUser=yes + StateDirectory)
ProtectSystem=strict               호스트 전체를 읽기전용으로
ProtectHome=yes                    /root, /home 접근 차단
PrivateTmp=yes
ReadWritePaths=/var/lib/organt/tenants/%i     자기 워크스페이스만 쓰기
NoNewPrivileges=yes                권한 상승 경로 차단
PrivateDevices=yes
RestrictSUIDSGID=yes
```
`permissions.py` 훅은 **그대로 둔다**. 훅이 1차(정책), 이 설정이 2차(능력)다. 훅이 새 도구를
놓쳐도 커널이 `/etc/murmur-web.env`와 타 테넌트 디렉터리를 물리적으로 못 읽게 한다. 지금
없는 건 이 2차 방어뿐이다.

**G3 (서버 단위 사용량 — 핵심)**
스키마를 바꾼다. 현재 `UsageLedger(person, period)` 옆에 서버 차원을 추가:
```python
class ProjectUsageLedger(models.Model):
    project = FK(Project)
    period  = CharField('YYYY-MM-DD', KST 일 버킷)   # 기존과 같은 버킷 규칙
    cost_usd, tokens_out, turns
    unique_together = ("project", "period")
```
러너가 이미 `report_usage`(guide HTTP)로 **채널 단위 증분**을 보내고 웹이 `pid→owner`로
해석해 적립한다. 즉 **pid는 이미 전달 경로에 있다** — owner로 접기 전에 project 축으로도
적립하면 된다. 기존 원장은 건드리지 않으므로 과금 로직 회귀 위험이 낮다.

그 위에 서버별 쿼터를 얹는다: `Project.daily_budget_usd`(null=무제한). 컨트롤 플레인이 봇을
깨우기 전에 그날 누적을 보고, 초과면 그 테넌트만 정지시키고 채널에 고지한다. 한 서버의 폭주가
다른 서버에 영향을 주지 않고, 호스트 전체 비용에도 상한이 생긴다.

**G4 (시끄러운 이웃)**
`botpool` 세마포어를 전역 1개 → **테넌트별 + 전역 2단**으로 바꾼다:
- 전역 상한 8 유지 (호스트 보호, 기존 동작)
- 테넌트별 상한 2~3 (한 서버가 전체를 못 먹게)
- 테넌트별 예약 1 (붐벼도 각 서버가 최소 1슬롯은 확보 — 기아 방지)

`botpool.py`는 순수 프로세스 로컬 모듈이라 키만 받게 바꾸면 되고, 전역 동작은 그대로 둘 수
있다(`ORGANT_MAX_SUBPROCS_PER_TENANT` 신규 env, 미설정 시 현행 동작).

**G5 (금고 키 단일 실패점)**
컨트롤 플레인이 마스터 `ORGANT_VAULT_KEY`를 갖고, 테넌트 워커에는 **그 테넌트 몫만 복호해
전달**한다(워커 env에 마스터 키를 넣지 않는다). 워커가 통째로 털려도 그 서버 시크릿만 나간다.
`_scrubbed_run_env()`가 이미 run 셸에서 비밀을 지우므로, 남은 건 워커 프로세스 env 자체의
범위 축소다.

**G6 (egress)**
서버 단위로 `WebFetch` 허용 도메인 목록(allowlist)을 두는 것을 제안한다. 지금은 전면 허용이라
워크스페이스 내용을 임의 URL로 보낼 수 있다. 최소한 감사 로그에 WebFetch 대상 URL을 남기면
(현재 PostToolUse 훅이 있으므로 자리는 있다) 사후 추적이 가능해진다. 전면 차단은 봇의 조사
능력을 죽이므로 allowlist + 로깅이 현실적이다.

### 3.3 수명 관리 (앞선 세션의 세션 라이프사이클과 결합)

테넌트 워커를 상시 12개 띄우면 baseline만 12 × ~115MB ≈ 1.4GB다. 14GB에서 감당은 되지만
낭비다. **on-demand 기동 + 유휴 종료**가 맞다:

- 컨트롤 플레인이 해당 서버에 일감(위임/멘션)을 감지 → `systemd-run`으로 워커 기동
- 봇 맥락은 프로세스가 아니라 디스크(`<sid>.jsonl`)에 있고 `resume`로 이어진다 —
  `_session_in_store()`가 이미 이걸 결정론으로 판정하므로 종료해도 기억이 안 끊긴다
- 유휴 15분 → 워커 종료(메모리 0). 다음 일감에 resume로 복귀
- resume가 공짜가 아니라는 실측(코드 주석: 프로브 회당 ~1cr = 캐시 재읽기)이 있으므로
  임계값을 너무 짧게 잡으면 손해다. 15분은 그 손익분기 위쪽을 잡은 값이고, 실측으로 조정 대상이다.

활성 서버가 보통 1~3개라면 상주 메모리는 1.4GB → 0.3GB 수준으로 떨어진다.

### 3.4 호스트 자원 구획

테넌트 슬라이스를 프로덕션 슬라이스와 분리한다(앞 세션 A계층과 동일한 구조, 테넌트 축 추가):
```
prod.slice          MemoryMin=3G    CPUWeight=1000   ← murmur-web/sse/postgres/nginx
organt.slice        MemoryMax=6G    CPUWeight=100    ← 컨트롤 플레인 + 전 테넌트 워커
  └ tenant-P-032.slice  MemoryMax=1.5G  TasksMax=128  CPUQuota=100%
  └ tenant-P-041.slice  ...
```
`prod.slice`의 `MemoryMin=3G`가 핵심이다. 어떤 테넌트가 폭주해도 커널이 프로덕션 메모리를
뺏지 않고, OOM은 그 테넌트 cgroup 안에서만 난다. **한 서버의 사고가 다른 서버도, 프로덕션도
건드리지 못한다** — 사용자가 말한 "원 서버 공격 차단"이 여기서 성립한다.

## 4. 단계별 적용

| 단계 | 내용 | 위험 | 효과 | 되돌리기 |
|---|---|---|---|---|
| 1 | `prod.slice` MemoryMin + `organt.slice` 상한 | 낮음 | 프로덕션 OOM 면역 | `set-property`로 즉시 |
| 2 | `ProjectUsageLedger` 추가 + pid 축 적립 (읽기 전용, 강제 없음) | 낮음 | **서버별 사용량 가시화** | 마이그레이션 되돌리기 |
| 3 | 서버별 쿼터 강제(`daily_budget_usd`) | 중간 | 사용량 폭 제한 | env 플래그로 off |
| 4 | botpool 테넌트별 세마포어 | 중간 | 시끄러운 이웃 차단 | env 미설정 시 현행 |
| 5 | 컨트롤/워커 분리 + 전용 UID + systemd 하드닝 | 높음 | **커널 레벨 테넌트 격리** | 유닛 교체 |
| 6 | 금고 키 범위 축소 / WebFetch allowlist | 중간 | 유출 표면 축소 | 설정 |

1·2는 관측과 안전만 추가하고 동작을 안 바꾸므로 먼저 하는 게 맞다. **2단계(서버별 원장)는
3단계 쿼터의 전제이자, 사용자가 지목한 "관리 가능성"의 실질**이다 — 지금은 어느 서버가
얼마나 태웠는지 볼 수단 자체가 없다.

5단계가 진짜 격리지만 러너 실행 모델을 바꾸므로 `ops/verify.sh` ALL_GREEN(920 tests) 통과를
전제로 해야 한다.

## 5. 트레이드오프와 열린 질문

- **워크스페이스 이전**: 전용 UID로 가려면 `/root/wt`(177MB) → `/var/lib/organt/tenants/`로
  옮기고 소유권을 바꿔야 한다. 세션 파일 경로가 cwd 슬러그 기반(`~/.claude/projects/<cwd-slug>/`)
  이라 **cwd가 바뀌면 기존 봇 세션 맥락이 끊긴다.** `_reset_session()`이 이 상황을 처리하지만
  이전 시 전 봇이 fresh로 재시작되는 비용을 감수해야 한다. 이전 타이밍을 고를 문제.
- **테넌트 수 확장**: 12개는 단일 호스트에서 충분하지만, 서버가 수십 개로 늘면 4코어/14GB가
  한계다. 그때는 이 설계가 그대로 다중 호스트로 확장된다(테넌트 워커가 이미 독립 유닛이므로
  다른 머신으로 옮기는 게 자연스럽다). 다만 guide 브리지가 127.0.0.1 직결 전제라
  (nginx에서 `/api/guide/` 외부 403) 그 부분은 재설계가 필요하다.
- **DynamicUser vs 고정 UID**: DynamicUser는 관리가 편하지만 UID가 바뀌어 워크스페이스 영속
  소유권과 안 맞는다. `StateDirectory=`와 함께 쓰면 해결되나, 고정 UID가 디버깅이 쉽다.

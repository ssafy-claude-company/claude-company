## 정향 요약 (감사 결과 — 2026-07-27)

결제 기반(`murmur/backend/sns/payments.py` 309줄)은 견고하다. 헤더의 안전 불변식(삼중 금액 대조·멱등·소유·카드 비접촉·키 미설정 잠김)은 코드·테스트에서 실재 확인. 감사에서 발견한 실제 구멍과 판단:

### A. 웹훅 — ★공식 규격 확인 결과가 사양의 전제를 정정한다
- **사실(공식 문서 실확인)**: 토스페이먼츠는 **일반 결제 웹훅(PAYMENT_STATUS_CHANGED·CANCEL_STATUS_CHANGED 등)에 서명을 제공하지 않는다.** 서명 헤더(`tosspayments-webhook-signature`)는 지급대행 이벤트(payout.changed·seller.changed) 전용. 웹훅 헤더는 transmission-id/time/retried-count뿐. 재시도는 최대 7회/3일 19시간.
  - 근거: docs.tosspayments.com/reference/using-api/webhook-events, docs.tosspayments.com/guides/v2/webhook (2026-07-27 열람)
- **따라서 "서명 검증을 붙여라"는 문자 그대로는 불가능**. 토스의 공식 보안 모델 = **payload 불신 + 시크릿 키로 결제 조회 API 재확인** — 현행 `pay_webhook`이 이미 그렇게 한다(paymentKey만 읽고 재조회, orderId 대조, DONE+금액 대조 후에만 확정). 즉 **위조 payload만으로는 현행 코드에서도 상태·요금제 조작이 안 된다**(기존 테스트 `test_웹훅_payload_위조는_무시` 실재).
- **남은 실구멍**(이번 수리 대상): ①무인증 공개 endpoint — 아무나 POST 가능, 유효 order_id 하나면 우리 서버가 토스로 아웃바운드 콜을 하게 무한 유발(증폭·자원 소모) ②스로틀 0 ③위조 시도 관측 0(로그 없음) ④방어가 "재조회 코드가 앞으로도 옳을 것" 한 겹뿐(심층 방어 없음).
- **수리 설계**: `TOSS_WEBHOOK_SECRET` env — 설정 시 `/api/pay/webhook/<비표>/`만 유효(비표는 constant-time 비교, 불일치·부재=403+상태 무변경+구조 로그), **미설정 시 기존 경로 그대로(무회귀)**. 웹훅 전용 스로틀(120/min/IP — 토스 재시도는 저빈도라 안전). 거부·무시 웹훅에 transmission-id 포함 로그. 재전송(리플레이)은 재조회 모델에서 본질적으로 무해(현재 상태 재동기화일 뿐, 확정·취소 깔때기 멱등) — 이벤트 id 멱등 테이블은 마이그레이션이라 이번엔 제외(관측 로그로 대체).
- **활성화(사용자 손)**: env에 TOSS_WEBHOOK_SECRET 추가 + 토스 개발자센터 웹훅 URL을 비표 포함 경로로 갱신. 코드만 배포해도 현행 동작 무변화.

### B. 승인↔부여 원자성 — 두 실구멍
- `_finalize_approved`는 Payment 행잠금 + 트랜잭션 내 부여로 이미 원자적. 그러나 **Person 행 잠금이 없어** 같은 사람의 다른 두 주문이 동시 확정되면 plan_until 연장이 lost update 될 수 있다 → Person도 select_for_update.
- **`pay_confirm`의 네트워크 예외 시 failed 마킹은 영구 미부여 구멍**: 토스 승인은 성공했는데 응답 수신이 끊긴 경우(타임아웃) failed로 박히고, `_reconcile_stale`은 **pending만** 조회하므로 대사가 영원히 안 잡는다(웹훅 등록돼 있으면 웹훅이 치유하지만 웹훅은 보조 경로). → NETWORK류 실패는 pending 유지("확인 지연" 응답), 확정 거절(토스가 명시 거부)만 failed.
- `_reconcile_stale`: DONE인데 금액 불일치면 아무 분기에도 안 걸려 **영원히 pending 재조회 반복** → failed+경고 로그(운영 검토 신호).
- 웹훅 취소 반영이 트랜잭션·잠금 없음 → 취소도 공용 깔때기(`_finalize_cancelled`)로 원자화, pay_cancel과 공용.
- 주기 대사 부재: 트리거가 pay_order 진입 시(본인 것)와 수동 커맨드뿐 → systemd 타이머 유닛 파일 제공(ops/systemd/, **설치는 사용자 승인 후**).

### C. 환불·취소 정책 (판단 = Fable, 사용자 확인 대기)
- **정책안**: ①전액 취소 = 그 주문의 부여기간(days) 회수, 지금 시각 밑으로는 안 내림(현행 `_revoke` 유지 — 스택된 다른 주문 기간은 보존) ②부분 환불(사용분 차감) = 그 주문의 서비스 종료로 간주, 동일 회수 ③운영자 무기한 수동 부여는 불건드림(현행) ④환불 창구는 당분간 운영자 수동(문의 → pay_cancel).
- 구현: `cancel_amount` 옵션(부분 환불 — 취소 전 토스 재조회로 balanceAmount 검증), 이미 취소 건 재요청은 무해 already 응답(멱등), 토스 ALREADY_CANCELED는 동기화 수용, raw에 취소 응답 보존, my_payments에 환불 합계 표시(raw.cancels 파생 — 저장 안 함).

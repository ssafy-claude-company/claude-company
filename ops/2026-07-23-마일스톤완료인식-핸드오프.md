# 마일스톤 완료 인식 갭 — 분석 (구현 핸드오프: GPT/codex)

> 작성 2026-07-23. 구현은 GPT가 함. 이 문서는 문제·근본·고칠 방향·검증을 담는다.
> 라이브 실측: ch94(P-045, task 181828-1). 백로그 릴레이는 작동했으나 판이 안 닫히고 순환.

## 1. 증상
백로그 릴레이(구조적 실행)는 실판에서 **작동한다** — ch94에서 백로그가 `[작업중] → 자동완료(backlog_autodone)`로 5개 연쇄, 게임 실물(server.js·public·tests)도 생성됨.
**그런데 마일스톤이 안 닫히고 판이 순환한다:**
- ch94 마일스톤 `MS-798869806-1`: **`met: 0, total: 2, status: "open"`** (완수조건 2개 중 0개 충족).
- 백로그는 다 done인데 마일스톤은 open → `flow_done → request_repick → open_task_restored → continue_incomplete` 순환(약 73분+).
- 결국 재픽업 상한 백스톱에 걸려 **`stalled_stopped`(repicks:2)로 종료** — 즉 무한순환은 아니지만 판이 **"완료(done)"가 아니라 "정체(stalled)"로 끝난다.** 목표(스스로 완주)와 다름. (5.4-low라 순환 비용은 작음.)

## 2. 근본 (비대칭) — ★검증 기계장치는 이미 다 있다, 촉발만 봇 의존
**중요:** 완수조건 검증→마감 파이프라인은 **이미 통째로 존재한다.** 없는 건 그걸 여는 트리거뿐.

이미 있는 것(`system/rule/milestone.py`):
- `Criterion`(43): `desc`(무엇이 충족) + **`verify`(run으로 실증 가능한 절차)** + `passed` + **`evidence`(검증 영수증)**. 등록 게이트가 desc+verify 둘 다 강제(소망형 거부).
- **`iter_verify(flow, obj, results)`**: `results=[{desc, passed, evidence}]`를 받아 조건 `passed` 마킹. **evidence 없는 passed는 거부**(허위 충족 차단). 전 조건 충족 → `obj.status="wrapup"`(잔여 정리 모드) → `wrapup_done`(전 SubTask done일 때만) → `status="done"`.
- `rule_report_iter`(봇 도구): 봇이 verify를 `run`으로 실행해 얻은 결과를 제출 → `iter_verify` 호출.

**갭(딱 한 칸):** `iter_verify`는 **봇이 verify를 실제 `run`으로 돌려 `results`를 만들어 `report_iter`로 제출**해야만 촉발된다. 그런데 봇들이 report_iter를 안 밟는다(2026-07-22 완료 게이트 약화 이후 잔재). → 조건 `passed=False` 유지 → `_ms_pending()`(`sys_core.py:2427`) True → 이어가기 루프(`sys_core.py:2476`)가 남은 백로그 없이 계속 → `continue_incomplete`(2682) → 재픽업 순환.

**비대칭:** 백로그 실행은 이미 구조가 대신 완료시킨다(`_claim_kick` autodone, 커밋 430d068). **마일스톤 조건 검증만 여전히 봇 자발 호출 의존.** 이 한 칸이 갭 — 그리고 채워 넣을 부품(`iter_verify`)은 이미 있다.

## 3. 고칠 방향 (GPT 구현) — 이미 있는 iter_verify를 구조가 촉발
백로그 autodone과 **대칭으로**, 마일스톤 완수조건 검증도 봇 자발 호출이 아니라 구조가 촉발하게 한다.
**새 검증 로직을 만들지 말 것 — `iter_verify`를 재사용**한다. 만드는 건 "언제·어떻게 조건 verify를 돌려 `results`를 만들 것인가"뿐.

**촉발 지점:** `sys_core.py` 이어가기 루프(2476~), `_claim_kick`(백로그 릴레이) **다음에** 마일스톤 검증 훅. 발동 조건 = `claim_kick_target(flow) is None`(집을/진행 중 백로그 없음 = 실행 소진) **그리고** 열린 마일스톤에 미검증(`not passed`, `status!="waived"`) 조건이 남음. 이때 아래 둘 중 하나로 `results`를 만들어 `iter_verify(flow, ms, results)` 호출.

**방법 A (권장 — SYS가 verify 직접 실행):** 조건별 `c.verify`(셸 절차)를 **작업공간에서 직접 `run`**해 exit 0 / 기대 출력이면 `{desc, passed:True, evidence: 출력요지}`, 아니면 `passed:False`. → `iter_verify`가 evidence 보고 마킹(허위 차단은 iter_verify가 이미 함). 가장 신뢰도 높음([[verify-live-before-claiming]]). **선결 과제:** SYS가 프로젝트 작업공간에서 셸을 돌리는 프리미티브가 필요 — 봇의 `run` 도구가 어떻게 작업공간(예: `organt_sns_workspace/<task>`)에서 실행되는지 찾아 재사용(핸들러·cwd·타임아웃). 이게 이 구현의 핵심 난소.

**방법 B (더 가벼움 — 봇을 구동해 report_iter 시킴):** `_claim_kick`이 백로그 작업자를 구동하듯, "완성됐으니 완수조건을 `verify`로 실증하고 `report_iter`로 제출하라"는 지시를 특정 봇에 주고 구동(상한 `ORGANT_BACKLOG_DRIVE_CAP` 대칭). 봇의 `run`을 그대로 쓰니 새 프리미티브 불필요 — 단 봇이 실제로 밟아줘야 함(백로그 릴레이에선 구동이 먹혔으니 가능성 있음). A가 안정적이면 A, 프리미티브 발굴이 크면 B로 시작해도 됨.

**공통 후단(이미 됨):** `iter_verify`가 전 조건 통과 판정 → `status="wrapup"` → (전 SubTask done 확인 후) `wrapup_done` → `status="done"`. 즉 A/B로 `results`만 정직하게 만들면 마감은 기존 파이프라인이 알아서.

**참조 패턴:** `_claim_kick`(sys_core.py) 구조적 autodone — 봇 자발 호출 대신 구조가 완료를 기록. 그걸 마일스톤 조건 검증에 대칭 적용.

## 4. 반드시 지킬 것 (거짓 완료 금지)
- **조건을 그냥 마킹하지 말 것.** `verify`를 실제 `run`으로 실행해 통과해야 `passed`. [[verify-live-before-claiming]] 원칙.
- verify가 통과 못 하면 마일스톤을 닫지 말고 **"사람 확인 필요"로 상신**(기존 `ms_consensus_empty`/blocked_pending 파킹 경로 재사용, `sys_core.py:2457~`).
- **무한 재검증 방지:** 조건별 검증 1~2회 시도 후 실패면 파킹(사람 대기), 성공하면 마감. (백로그 autodone의 구동 상한 `ORGANT_BACKLOG_DRIVE_CAP`과 대칭으로 상한 두기.)
- verify 절차가 비었거나 실행 불가(인프라 벽)면 blocked_pending으로 사람 승인 대기(`renegotiate_criterion` 경로).

## 0. 이미 갖춰진 안전 불변식 (건드리지 말 것 — 회귀 금지)
`payments.py` 헤더와 `Payment` 모델 주석에 박제된 것들. 재작업 중 깨뜨리면 안 된다.
- **금액 신뢰 0**: 승인 시 주문금액 == 요청금액 == PG 승인금액(totalAmount) **삼중 대조**. 금액은 서버가 정한다.
- **멱등**: `order_id` unique·서버 발급 난수. 재승인 요청은 무해 반환(이중 부여 없음).
- **소유**: 주문 생성자 본인만 승인 요청 가능. 게스트 결제 불가.
- **카드정보 비접촉**: 토스 결제창만 카드를 다룬다(우리 서버 무접촉 = PCI 범위 최소화). `raw`엔 마스킹 응답만.
- **키 미설정 = 기능 잠김(503)**: 안전한 기본값(무회귀).
- **탈퇴해도 결제 이력 보존**: `person`은 SET_NULL, 재무 감사 기록은 계정과 독립.

## 1. 작업 순서 (우선순위 = 위험도 순)

### A. 웹훅 서명 검증 — ★최우선 (실측된 구멍)
`payments.py:263 pay_webhook`에 **서명/HMAC 검증 흔적이 없다**(`grep -i "signature\|hmac"` 무소득).
- **위험**: 그 주소를 아는 누구나 "결제 취소됨" 등을 **위조 전송** → 남의 유료 요금제를 끊거나 상태를 조작. 인증 없는 상태 변경 경로다.
- **할 일**: 토스페이먼츠 웹훅 서명 검증을 붙여라(공식 규격 확인 — 헤더 서명/시크릿 기반). 검증 실패 = 401/403 + 상태 변경 0. 재전송 공격 방지(타임스탬프·이벤트 id 멱등)도 함께.
- **수용 기준**: 위조 웹훅(서명 없음/틀림/만료)이 `Payment.status`와 `Person.plan`을 **전혀 바꾸지 못한다**는 회귀 테스트. 정상 서명 웹훅은 그대로 동작.

### B. 승인↔권한 부여 원자성·정합 감사
- 승인은 성공했는데 `Person.plan`/`plan_until` 부여가 누락되는 틈(예외·부분 실패·중복 승인)이 없는지 감사.
- 트랜잭션 경계와 실패 시 복구 경로(수동 보정 아닌 자동 정합)를 확인·보강.
- `reconcile_payments` 커맨드가 **실제로 그 틈을 잡아내는지** 검증하고, 부족하면 보강(PG 조회 대조 → 불일치 리포트/자동 보정).
- **수용 기준**: 승인 성공 = 요금제 부여, 둘 중 하나만 성립하는 상태가 남지 않음(테스트로 박제).

### C. 환불·취소 경로 완성
- 사용자/운영자 취소, 부분 환불, 환불 시 `plan_until` 회수 규칙(즉시 회수 vs 잔여기간)을 **정책으로 확정하고 코드로 박제**.
- 환불도 멱등(중복 환불 요청 방지)·감사 기록 보존.
- **수용 기준**: 취소·환불이 원장과 권한에 정확히 반영되고, 재시도해도 이중 처리 없음.

### D. 전자상거래법·사업자 고지 의무 (실서비스 필수)
사업자로 실제 판매하므로 법적 표기가 빠지면 안 된다.
- **사업자 정보 표기**: 상호·대표자명·사업자등록번호·통신판매업 신고번호·주소·연락처·이메일 — 보통 푸터·결제 화면·이용약관에 노출.
- **필수 문서**: 이용약관, 개인정보처리방침, **환불·취소 정책**(디지털 콘텐츠/구독 특성 반영).
- **결제 전 고지**: 금액·기간·자동갱신 여부·해지 방법을 결제 직전에 명확히.
- **영수증**: 결제 내역·영수증 확인 경로(`/me/payments/` 이미 있음) 정비.
- 실제 사업자 정보 값은 **사용자에게 물어라**(임의 창작 절대 금지 — 허위 표기는 법적 문제).
- **수용 기준**: 결제 화면·푸터에서 위 항목이 실제로 보이고, 값은 설정(환경변수/사이트 설정)으로 관리되어 하드코딩되지 않음.

### E. 고도화 (위가 끝난 뒤)
정기결제(자동갱신)·영수증 개선·세금계산서·요금제 변경(업/다운그레이드 비례정산) 등. **A~D 없이 손대지 마라.**

## 2. 규율
1. **검증은 오프라인** — `bash ops/verify.sh`. 실 결제 창을 검증 목적으로 띄우지 마라. 토스 **테스트 키**로 대역 검증하고, 실키는 절대 코드·로그·문서에 남기지 마라.
2. **비밀값 취급**: 시크릿 키는 서버→PG 호출에만. 로그·응답·커밋에 키 노출 0. 노출 의심 시 즉시 보고.
3. 조어·사적 기호 금지, 기존 관례 준수. 사실이 바뀌면 `ops/STATE.md` 갱신.
4. 라이브 인프라(웹 재시작·`/etc`·env 파일) 변경은 **사용자 승인 후**. 마이그레이션도 승인 후.
5. 판단·설계는 네가 직접(Fable).
6. **★ 핸드오프 의무**: 세션이 중간에 끊길 수 있다(선례: Fable 세이프가드로 세션 중단). **의미 있는 진전마다** 이 문서 옆에 진행 상태·다음 할 일·근거를 갱신해 남겨라. 다음 세션이 그것만 읽고 이어받을 수 있어야 한다.

## 3. 착수 방식
먼저 `payments.py` 전체와 `Payment`/`Person.plan` 모델, `urls.py`의 결제 라우트, 기존 테스트를 정독하고 **정향 요약 + 작업 계획**(A~D 각각 무엇을 어떻게 고쳐 어느 수용 기준을 충족하는지)을 사용자에게 낸 뒤 착수하라. 사업자 정보 등 사용자만 아는 값은 그때 함께 질문하라.
